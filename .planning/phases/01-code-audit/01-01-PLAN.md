**Audit checklist — examine each of these in app.py and score them:**

1. **Auth bypass paths** (lines 69-88): Can `require_auth` be bypassed? What happens when `auth.password` is None? Does `hmac.compare_digest` handle None input safely? Check line 81 specifically — if `auth` exists but `auth.password` is None, what does `hmac.compare_digest(None, BACKUP_PASS)` do?

2. **Docker socket exposure** (docker-compose.yml line 40): Full socket access vs socket-proxy. What API calls does the app actually make? Does the socket-proxy in secure.yml actually cover all needed calls? Check if `exec_create` and `exec_start` work through the proxy.

3. **Input injection risks**:
   - Line 199: `cmd=["python", "manage.py", "document_exporter", EXPORT_PATH_IN_CONTAINER]` — is EXPORT_PATH_IN_CONTAINER sanitized? Can env var injection lead to command injection?
   - Line 250: `["tar", "-czf", archive_path, "-C", EXPORT_PATH_IN_CONTAINER, "."]` — can archive_path or EXPORT_PATH_IN_CONTAINER contain shell metacharacters?
   - Line 388: Path traversal check — is `"/" in filename or "\\" in filename or filename != Path(filename).name` sufficient? What about null bytes, encoded slashes, or `..`?

4. **Secret handling**: Credentials in env vars (lines 41-42), visible in `docker inspect`, process listing, compose files. No Docker secrets support.

5. **CSRF on state-changing endpoints**: `/backup/stream` (GET that triggers backup — GET should be safe/idempotent per HTTP spec), `/backup/abort` (POST). Can a malicious page trigger a backup or abort via cross-origin request?

6. **Health endpoint information disclosure** (line 284-288): `/health` has no auth — does it leak sensitive info?

7. **SSE stream without connection validation**: Lines 210-214 — does the generator continue running if the client disconnects? What are the resource implications?

8. **Timing attacks**: Line 81 uses `hmac.compare_digest` (good), but `auth.username != BACKUP_USER` on the same line uses standard string comparison — is this a timing leak for the username?

For each finding, assign severity:
- CRITICAL: Directly exploitable, leads to RCE or data loss
- HIGH: Exploitable with some conditions, significant impact
- MEDIUM: Requires specific conditions, limited impact
- LOW: Theoretical risk, defense-in-depth improvement

**Implementation bugs to examine:**

1. **Health endpoint return value** (line 288): `return jsonify({"status": "ok", "docker": docker_ok}), 200 if docker_ok else 503` — Python operator precedence means this returns `(jsonify(...), 200)` when docker_ok is True (a tuple, not a proper response) and `(jsonify(...), 503)` when False. The `200 if docker_ok else 503` is the second element of a tuple. Check: does this actually return the correct status code in both cases? The comma makes this `return (json_response, status_code)` which Flask handles — but verify the precedence: is it `(jsonify(...), (200 if docker_ok else 503))` or `(jsonify(...), 200) if docker_ok else 503`?

2. **Abort mechanism incomplete** (lines 354-380): CONCERNS.md documents this. After `_current_container` is set to None (line 217), abort returns 400 but tar/retention continues. Verify: is there any way to abort during tar phase? During retention? What does the user see?

3. **Exit code race** (lines 218-222): `exec_inspect` called immediately after stream ends. If exit code is not yet available (returns None), backup proceeds with a warning (line 229-230). The archive is created from potentially incomplete/corrupt export data. This is documented in CONCERNS.md — verify the exact behavior.

4. **Container detection logic flaw** (lines 109-124): When `PAPERLESS_CONTAINER_NAME` is set, line 111 skips containers that don't match the name. But line 123 checks `if not (image_match or name_match or PAPERLESS_CONTAINER_NAME)` — so when `PAPERLESS_CONTAINER_NAME` is set, this condition is always False (because `PAPERLESS_CONTAINER_NAME` is truthy), meaning the container passes even without image or name match. Trace the logic: if container.name matches PAPERLESS_CONTAINER_NAME but image tag doesn't match and "paperless" isn't in the name, does it still get selected? (Yes — line 123 passes because `PAPERLESS_CONTAINER_NAME` is truthy.)

5. **`_abort_requested` never cleared on normal completion** — line 175 clears it at start of `run_backup_generator()`. But if backup completes normally and user never clicked abort, `_abort_requested` remains cleared (fine). What if abort is clicked AFTER backup completes but BEFORE next backup starts? The event stays set. Next backup starts, line 175 clears it — OK. But what about line 224 check? If abort was requested during the gap between backups, it's cleared by line 175 before the check at line 224. This seems correct. Verify.

6. **`apply_retention` stat race** (lines 150-153): Archives sorted by mtime, but between sort and unlink, a file could be deleted by another process. The except on line 161 handles this — but is it correct?

**Robustness gaps to examine:**

1. **Broad exception handling** (multiple locations): Lines 62, 105, 117, 161, 203, 220, 264, 309, 376 — all catch generic `Exception`. For each: what specific exceptions should be caught? What information is lost?

2. **No timeout on Docker exec streaming** (lines 210-214): If Paperless hangs, the backup stream hangs indefinitely. Gunicorn timeout is 3600s — so after 1 hour it kills the worker. What happens to the lock? To _current_container?

3. **Subprocess tar without timeout** (line 249): `subprocess.run()` with no `timeout` parameter. For very large exports, tar could run for hours. What happens?

4. **Memory usage during streaming** (lines 210-214): Each chunk decoded and split into lines. No backpressure if client disconnects. Generator continues running until Docker exec completes.

5. **`_backup_lock.locked()` is not reliable** (line 313, 358): `.locked()` returns True if ANY thread holds the lock — but between checking and acting, the lock state can change. This is a TOCTOU (time-of-check-time-of-use) issue. How does this manifest in `/status` and `/backup/abort`?

6. **Integer conversion of BACKUP_KEEP_LAST** (line 39): `int(os.environ.get("BACKUP_KEEP_LAST", "7"))` — if user sets non-numeric value, app crashes on startup with ValueError. No validation or error message.

7. **No disk space check before tar** (lines 249-253): If disk is full, tar fails with an error. But partial archive may be left behind, consuming space and appearing in the archive list.
